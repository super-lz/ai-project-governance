# AI Project Governance

这是一套可复制到其他项目的 AI 开发维护治理包。目标是把长期依据压缩到少数可靠来源，让真实大型项目可以持续演进，而不是被临时对话、过程文档和重复技术文档拖乱。

核心规则必须落进项目仓库，而不是只存在于某个 AI 工具或 skill 中。skill 可以帮助复制、合并、追问和审查，但不能替代项目内的 `AGENTS.md` 和实现规格。

## 核心模型

项目长期依据只保留三类：

- 实现规格：承接产品目标和已确认的实现决策，说明要实现什么行为、边界和验收标准。
- 代码本身：说明行为实际上如何实现，类型、模块边界、测试和必要注释承担主要技术说明。
- Git 历史：追溯为什么发生变动、何时发生变动和变动范围。

AI 对话、临时计划和开发过程记录只用于形成当次决策，不作为长期依据。稳定决策必须进入实现规格或代码，真实变动必须能从 git 历史追溯。

## 包结构

```text
ai-project-governance/
  README.md
  template/
    AGENTS.md
    docs/
      AGENTS.md
      spec/
        AGENTS.md
        main-spec.md
      appendix/
        README.md
```

## 使用方式

1. 把 `template/` 里的 `AGENTS.md` 和 `docs/` 复制到目标项目根目录。
2. 把 `docs/spec/main-spec.md` 重命名为当前项目的主实现规格，例如 `docs/spec/<project-or-system>.md`。
3. 修改根 `AGENTS.md` 和 `docs/spec/AGENTS.md` 中的主规格文件名。
4. 后续开发时，先读根 `AGENTS.md`，再按任务需要读取目录入口和主实现规格。

## 推荐开场

没有现成产品文档时：

```text
请按本项目 AGENTS.md 工作。我们要做 <项目目标>。
先不要写代码，先和我一起把 docs/spec/<name>.md 的实现规格梳理清楚。
你需要主动追问会影响实现的关键决策，最后输出可直接进入开发的规格。
```

已有产品文档时：

```text
请按本项目 AGENTS.md 工作。
根据我提供的产品文档，帮我整理 docs/spec/<name>.md。
不要写开发日志，不要写重复代码的技术文档。
只沉淀稳定的实现规格、阶段边界和验收标准。
```

## 何时新增文档

默认不新增长期技术文档。只有以下情况才新增：

- 复杂技术调研需要保留证据。
- 实现规格过长，需要按系统边界拆分。
- 给人理解的辅助图、草图或说明需要放入 `docs/appendix/`。

不新增开发日志、每日进度、临时计划、重复代码结构的技术说明。

## 何时做成 skill

模板应该先落进项目。等多个项目验证稳定后，可以再做一个 skill 来自动化以下动作：

- 检查项目是否已有 `AGENTS.md` 和 `docs/spec/`。
- 合并模板而不是覆盖已有规则。
- 引导用户把产品目标沉淀成实现规格。
- 审查实现规格是否足够进入开发。
- 检查是否混入 AI 对话原文、开发日志、临时计划或重复代码的技术文档。

skill 负责应用模板；模板本身仍应进入目标项目仓库。
