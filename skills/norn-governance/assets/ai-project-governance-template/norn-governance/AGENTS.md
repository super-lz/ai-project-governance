# Norn 治理入口

本目录保存 Norn 管理的项目规格、临时计划和附录材料。进入本目录创建或修改内容前，先读本文件，再根据任务读取对应子目录入口。

## 区域职责

- `spec/`：实现规格。这里的文档是代码实现、测试和验收的主要依据。
- `plans/`：临时执行计划。这里只保存进行中或阻塞任务的剩余工作、下一步和验证状态，不是实现依据。
- `appendix/`：附录辅助材料。这里的文档面向人类快速理解，可以是流程图、草图或临时辅助说明，不作为实现依据。

## 临时计划

- 只有任务预计跨会话、跨设备、包含多个相互依赖步骤或明显容易中断时，才创建计划；简单任务继续使用当前上下文。
- 一个独立任务对应一个 Markdown 文件，文件名使用稳定、可识别的短横线命名；不创建全局 `current-plan.md`。
- 计划至少写清目标与非目标、依据、已完成、剩余、下一步、验证状态和阻塞项，不复制完整对话、命令流水或分析过程。
- 计划允许随开发分支提交和推送，以支持跨设备或协作者接续。恢复任务时先验证分支、规格、代码和 Git 状态，再使用计划。
- 只读取与当前任务匹配的计划，不扫描或加载无关计划。
- 在关键实现或验证检查点更新计划，不为每条命令记录进度。
- 计划与规格、代码或 Git 冲突时，计划视为过期导航；先依据真实现状重新确认，不能按旧计划覆盖事实。
- 任务完成或取消后，将稳定结论沉淀到规格、代码、测试或必要注释，再删除计划文件。阻塞任务可以保留，但必须写清阻塞条件和恢复后的第一步。
- 不创建计划索引、完成归档、README 或 `.gitkeep`。没有未完成计划时，`plans/` 可以不存在。

## 治理规则

- 不把开发过程、临时计划、每日进度写入规格或附录。
- AI 对话和临时计划只承接短期执行状态，不作为长期依据；稳定决策必须进入实现规格或代码，真实变动必须能从 Git 历史追溯。
- 不新增长期技术文档来重复代码实现；代码、类型、测试和必要注释承担主要技术说明。
- 不新增与最终目的无关的长期文档；每份长期文档都必须说明它服务的真实需求、稳定决策或必要证据。
- 只有复杂技术调研需要保留证据时，才新增短文档；调研结论必须回到实现规格或代码。
- 新材料优先放入现有分类。只有分类语义不够用时，才新增目录，并补对应入口说明。
